# Skill: Structure First (Korean Pair)

> 영문 기본 문서: `SKILL.md`
> 설명 동기화: 관련 동작이나 판단 소유를 추적하기 어렵거나, 부작용이 검증을 가리거나, 경계가 늘어나거나, 제안된 구조가 복잡도를 줄이지 않고 이동시킬 수 있는 구체적인 legibility 문제가 나타날 때 쓰는 스킬입니다. 작업이 비사소하다는 이유만으로 선택하지 않으며 기존 단위가 일관된 국소 변경을 이미 수용하면 건너뜁니다.

## Purpose

> **Primary Flow**: 명령형 오케스트레이션이 자연스러운 로직을 위에서 아래로 읽히게 만드는 메인 성공 경로

관련 동작을 그 코드에 자연스러운 읽기 형식으로 추적한 뒤, 이해·변경·검증을 실제로 어렵게 만드는 지점을 다룹니다. Primary Flow, Atom, composition point와 side-effect boundary는 관찰된 문제에 대한 후보 반응이지 필수 결과 형태가 아닙니다.

복잡도를 없애거나 실제로 독립적인 책임 뒤에 격리하는 변경을 선호합니다. 기존 구조가 일관된 변경을 이미 수용하면 유지하고, 바뀐 동작은 구현 추종이 아닌 **계약 중심(contract-driven)** 테스트로 보호합니다.

## Use / Do Not Use

- 요청된 변경에서 동작을 추적하기 어렵거나, 책임·판단 소유가 불명확하거나 중복되거나, 부작용이 검증을 가리거나, 경계가 늘어나거나, 복잡도 이동이 의심되는 구체적인 문제가 나타날 때 쓴다.
- 위 문제가 범위에 포함된 구조 중심 코드 리뷰에 쓴다.
- 계획 수립, 분류, 스코프 분석에서는 응답 템플릿으로 강제하지 말고 내부 판단 렌즈로만 쓴다.
- 사용자에게 보이는 버그나 UI 오작동은 먼저 관찰 가능한 동작을 규명하고, 그 동작에 대한 현재 작업 단위의 책임이 분명해진 뒤에만 구조 작업을 적용한다.
- 기능 작업, 버그 수정, 리팩터링이거나 비사소한 작업이라는 이유만으로 선택하지 않는다.
- 기존 단위가 작은 일관된 변경을 이미 수용하고 구체적인 legibility 문제가 없으면 쓰지 않는다.
- 1회성 실험/탐색 코드에는 쓰지 않는다.
- 아주 작은 수정인데 구조 개입이 과해지는 경우에는 쓰지 않는다.

## Core Bias

- 추적 가능한 동작과 소유권 > 구조적 단순성 > 재사용성 > 추상화
- 미래 가능성보다 **현재 코드의 명확성**을 우선한다.
- 구조 변경은 목적이 아니다. 유지, 인라인, 결합, 삭제, 추출은 모두 정상적인 결과다.

## Operating Model

증상이나 결과가 나타난 위치만 따르지 말고, 바꾸려는 동작이나 규칙을 책임지는 가장 작은 **현재 작업 단위(current unit)**를 고른다.
로컬 수정은 보통 함수/파일, 기능 작업은 모듈/유스케이스, 더 큰 리팩터링은 capability/subsystem 단위가 된다.

1. **동작 추적**
- 의도와 가장 작은 관찰 가능한 완료 조건을 한 문장으로 적는다.
- 명령형 흐름, 상태 전이, 이벤트 생명주기, 규칙 집합, 데이터 흐름, 프로토콜 경계처럼 그 코드에 자연스러운 읽기 형식으로 동작을 따른다.
- 그대로 두면 요청 동작, 계약이나 의미 있는 검증이 깨지는 호출부, 타입, 테스트, 문서, 설정만 포함하고 인접 정리는 제외한다.

2. **구체적인 마찰 명명**
- 읽기 어려운 인과 경로, 불명확하거나 중복된 책임, 숨은 부작용이나 실패 의미, 늘어나는 경계처럼 동작을 실제로 이해·변경·검증하기 어렵게 만드는 지점을 찾는다.
- 현재 단위가 변경을 일관되게 수용하면 구조를 유지한다.

3. **의미 있는 구조 선택만 탐색**
- 국소적인 명확화와 구조 변경이 둘 다 신뢰할 만한 후보일 때만 비교한다.
- 유지, 인라인, 결합, 삭제, 순서 변경과 추출을 동등한 후보로 다룬다.
- Primary Flow는 명령형 오케스트레이션을 명확하게 할 수 있다. Atom은 관련 없는 책임과 함께 조정하지 않고도 동작을 바꿀 수 있는 독립적으로 이해 가능한 역할이다. 크기, 순수성, 추출 여부는 원자성의 가능한 증거이지 요구사항이 아니다.
- 조합은 자연스러운 소유자에서 발견 가능하게 한다. 하나의 오케스트레이터를 만들기 위해 관련 없는 판단이나 생명주기를 중앙화하지 않는다.
- 부작용의 소유권과 실패 의미가 보이게 한다. 별도 경계가 추론, 검증, 재시도나 교체를 실질적으로 개선할 때만 부작용을 격리한다.

4. **전체 효과로 선택**
- 복잡도를 없애거나 독립 책임 뒤에 유용하게 격리할 때만 구조 변경을 선택한다.
- 짧아진 상위 흐름이 복잡도를 도우미 체인, 감싸기 계층, context 객체, 설정, 숨은 상태, 오류 채널이나 추가 생명주기로 옮긴 것은 아닌지 본다.
- 미확정 선택에 사용자 권한이 필요하거나 공개 API, 데이터, 보안, 의존성·비용, 마이그레이션에 되돌리기 어려운 약속을 만들 때만 결정을 요청하고 멈춘다. 그렇지 않으면 되돌릴 수 있는 국소 가정을 사용하고 알린다.

## Growth and Ownership

- 공개 I/O/시그니처는 확정된 책임만 담는 최소 형태로 시작하고, 책임이 실제로 바뀔 때만 키운다(새 외부 입력, 의미 혼합, 경계 이동).
- 확인되지 않은 미래 사용을 위해 옵션, 설정, 의존성, 추상화를 추가하지 않고, 이번 변경으로 쓰이지 않게 된 코드는 제거한다.
- 정책, 판단, 계산 규칙마다 비경쟁적인 resolution path를 둔다. 단일 소유자, 명시적인 조합 순서, 조정·충돌 해결 protocol일 수 있다.
- 외부에서 보이는 write 소유권을 발견 가능하게 한다. 여러 writer가 의도된 경우 기본적으로 중앙화하지 말고 조정·충돌 계약을 드러낸다.
- 더 큰 스케일에서는 관련 진입점, 조합이나 조정, 판단 resolution을 발견 가능하게 한다.
- 비동기 경계의 최신성·완료 resolution path를 명시한다. 단일 소유자일 수도 있고 protocol일 수도 있다.
- 판단 규칙 소유가 바뀌거나 새 동등 경로를 넣는다면, 가능하면 같은 변경에서 기존 경로를 제거/비활성화한다. 어렵다면 단계적 마이그레이션 계획(소유자, 종료 조건)을 함께 남긴다.
- `판단 규칙(Decision rule)`: 동작을 결정하는 반복 조건, 가중치, 우선순위, 정책, 계산, 키 생성 규칙.
- `동등 경로(Equivalent path)`: 외부에서 관찰되는 결과가 같은 대체 실행 경로.

## Testing

- 가능한 한 책임을 소유하는 가장 안정적인 단위에서 테스트를 충분히 작성
- 구현 세부가 아니라 현재 작업 단위와 소유 역할/경계 사이의 **계약(I/O, 불변조건, 경계값)**을 검증
- 위험과 변경 종류에 검증을 맞춘다. 버그는 수정 전에 재현하거나 현재 동작을 규명하고, 리팩터링은 전후의 안정 동작을 확인하며, 기능은 성공·실패·관련 경계를 검증한다. 가능한 원인을 여러 개 한꺼번에 바꾸기 전에 실패를 좁히고, 검사를 실행할 수 없으면 이유와 다음으로 유용한 검사를 밝힌다.
- 오케스트레이션이나 경계 통합이 주요 리스크라면 현재 작업 단위를 직접 테스트한다
- 비동기/상태성 경계가 있다면 stale 결과 처리, 완료 균형, 동등 입력 no-op 같은 ownership 계약을 그 경계를 소유한 가장 안정적인 단위에서 검증한다
- 이번 변경에서 테스트를 추가할 수 없다면 그 사실을 명시하고, 다음 안정적인 책임 단위와 필요한 계약 케이스를 함께 적는다
- 테스트 코드도 읽히게 유지: `each`/table 케이스로 중복을 줄이고, 구조를 흐리지 않는 작은 헬퍼만 허용하며, 테스트 하나는 핵심 주장 하나에 집중한다

## Anti-Patterns

- 분리 후 인자/상태 전달이 늘어나면 되돌리기
- 보기 좋으려고만 함수/파일 분리하지 않기(유틸 난립 금지)
- 상위 흐름을 짧게 보이려고 복잡도를 도우미 체인, 감싸기 계층, context 객체, 설정, 숨은 상태, 오류 채널이나 추가 생명주기로 옮기지 않기
- 이름이 설명문처럼 길어지면 경계를 재검토
- 미래 재사용 가정의 추상화/레이어 추가 지양
- 테스트에서 과도한 추상화/헬퍼 난립 지양
- "나중에 필요할 수도 있음" 이유로 인자 선추가 금지
- 동일 정책, 판단, 계산, 키 생성 규칙의 다중 소유 금지
- 여러 writer를 조정하는 것 자체가 명시적 책임이 아닌데도 같은 외부 관찰 결과를 여러 writer 위치에 나눠두지 않기
- ownership과 reset 의미가 명시적이지 않은데도 상위 경계의 상태를 로컬 가변 상태로 동기 미러링하지 않기
- 한 unit이 읽은 입력/update 경로에 다시 그 경로로 써 넣는 self-feedback loop를 만들지 않기
- 단계적 마이그레이션 계획(소유자, 종료 조건) 없이 동등한 신규/구경로 병행 유지 금지

## 위험에 맞춘 검토

관찰된 문제와 관련 있는 질문만 사용한다.

- 관련 동작과 판단 소유권을 전보다 쉽게 추적할 수 있는가?
- 복잡도가 제거되거나 독립 책임 뒤에 격리됐는가, 아니면 도우미, 감싸기 계층, context, 상태, 오류 채널이나 생명주기로 이동했는가?
- 새 경계가 실제 책임, 부작용이나 계약에 대응하는가?
- 바뀐 관찰 동작과 계약을 검증이 보호하는가?

## Optional Completion Evidence

이 템플릿은 구조 자체를 설명하는 것이 핵심일 때만 쓴다. 그 외에는 자연스럽게 응답한다.

형식이 실제로 유용한 경우에만 아래 항목을 제시:

- `Current Unit:` function/file | module/use case | capability/subsystem
- `Observed Problem:` 구체적인 legibility 문제 또는 `none; structure unchanged`
- `Readable Behavior:` 변경 뒤의 자연스러운 인과/읽기 형식
- `Structural Choice:` kept | inlined | merged | deleted | reordered | extracted와 그 이유
- `Tests:` `added ...` 또는 `deferred because ...; next stable unit(s): ...; required contract cases: ...` (해당되면 freshness/completion contract 포함)

판단 규칙 소유가 바뀌는 리팩터링에서는 아래 항목을 함께 제시:

- `Decision Ownership:` `policy/decision/calculation/key-generation rule -> owner unit`; 중복 소유 제거 여부 yes/no

시그니처/경계가 커졌거나 구경로를 대체한 리팩터링에서는 아래 1줄을 함께 제시:

- `Refactor Check:` 인자 증가 근거 / 구경로 상태(제거·비활성화·마이그레이션 계획)
